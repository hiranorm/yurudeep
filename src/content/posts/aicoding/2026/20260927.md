Claude（Anthropic）との共同編集により作成されました。

:::tip[要約]
* 同じ資料・同じ依頼から、Claude Code に Slidev と ppt-master の両方で勉強会用のスライドを作らせた。**ppt-master は推奨設定のままだと、1枚あたりの文字量が Slidev 版の約5倍**（約500字 対 約100字）になった
* 見た目の完成度は ppt-master が上。ただ、発表者ノートを暗記せずに口頭で説明するスタイルには情報量が多すぎる。実際に ppt-master のスライドで発表すると、想定より長くなることが多かった
* Slidev は `CLAUDE.md` に情報量の上限を書くだけで、エージェントがそれに従う。PNG 書き出しは12枚で約6.5秒なので、作って見て直すループを何度も回せる。ppt-master はワークフロー全体で約28.5分、途中で決める項目も約25個あった
* **今後の発表は Slidev を使う**。Marp より表現力があり、ppt-master より表現力で劣る代わりに、詰め込みになりにくく作るのが速い。ppt-master は、読まれる資料や PowerPoint で渡して編集してもらう資料に使う
:::

ppt-master で作ったスライドで発表すると、なぜか時間が押す。スライド自体はプロが作ったように見えるし、構成もしっかりしている。なのに話し終わるといつも想定より長い。

前の記事で [AIエージェント前提のスライド作成ツールを比較](/posts/aicoding/2026/20260926/) し、技術登壇なら Slidev、編集可能な PPTX なら ppt-master という整理になった。ただ、机上の比較では「エージェントに任せたとき、どんなスライドが出てくるか」までは分からない。そこで、その比較記事の元になった調査資料を題材に、両方で勉強会用の要約スライドを作らせて並べてみた。

---

## 結論：今後の発表は Slidev を使う

先に結論を書いておく。**口頭で話す発表には Slidev を使う**ことにした。

Slidev は Marp よりも表現力があり、ppt-master よりは表現力で劣る。その代わり、詰め込みになりにくく、作るのが速い。ppt-master は見た目の完成度では上だが、推奨設定のままだと1枚に説明・注意・補足まで入り、「読む資料」の密度になる。発表時間が延びていた原因はこれだった。

## 試した条件

| 項目 | Slidev | ppt-master |
|---|---|---|
| 入力 | 比較記事の元になった調査資料（同じファイル） | 同じ |
| 依頼 | 勉強会で発表する要約スライド、日本語 | 同じ |
| バージョン | @slidev/cli v53.0.0、default テーマ<sup>1</sup> | v6.6.0（2026-09-19）<sup>4</sup> |
| 進め方 | 構成と情報量のルールを `CLAUDE.md` に書き、エージェントが作成 → PNG で確認 → 修正 | Generate PPTX の Default ルート。確認ゲートの選択肢はすべて推奨を採用<sup>5</sup> |
| エージェント | Claude Code（Claude Opus 5.5） | 同じ |
| 環境 | macOS 27.0、Node.js 26.9 | 同じ（Python は venv） |

ppt-master には、使う前から不満が3つあった。フォーマットやフォントの自由度は高いが選択肢が多すぎること、毎回同じテンプレートにしにくいこと、エリアを分割して矢印を入れても話すときに分かりやすくなるとは限らないこと。今回はこれらを気にせず、推奨設定のまま作った。

## Slidev での作り方

### 情報量の上限を CLAUDE.md に書く

1. 公式の Agent Skill を読ませた。Skill は `@slidev/cli` パッケージに同梱されていて（`node_modules/@slidev/cli/skills/slidev/`）、`npx skills add slidevjs/slidev` でも導入できる<sup>2</sup>
2. プロジェクト直下の `CLAUDE.md` に、情報量の上限を書いた
3. エージェントが `slides.md` を書き、`slidev export --format png` で全ページを画像にして確認し、直した
4. 見た目の調整は `style.css` だけで行い、フッターは `slide-bottom.vue` で付けた

`CLAUDE.md` に書いたルールを抜粋すると次のとおり。

```markdown
## 情報量の上限（詰め込み防止）

- 1スライド1メッセージ。見出しはそのメッセージを言い切る文にする（「〜について」で終わらせない）
- 箇条書きは最大4項目、1項目は全角30字以内。入らない内容は発表者ノート（`<!-- -->`）へ回す
- 表は最大 4行 × 4列（ヘッダ行を除く）。セルは全角15字以内
- コードブロックは最大12行
- 本文に入れなかった補足・数値の出典は、必ず発表者ノートに書く

## 自己検証（必須）

編集したら必ず PNG に書き出し、見てから完了とする。
確認すること：はみ出していないか / 下端に要素が詰まっていないか / 1枚に言いたいことが2つ以上ないか。
```

公式 Skill は、構文とリファレンスへの索引が中心だった。「1スライド1メッセージ」のような、デザインや情報量についての規律は入っていない<sup>2</sup>。ppt-master がデザインの考え方まで Skill の中に持っているのとは対照的だ。そのため情報量のルールは自分で書く必要があるが、逆に言えば**情報量を自分で完全に決められる**。今回の比較でいちばん効いたのはここだった。

### 3回の確認で仕上がった

12枚すべての PNG 書き出しは約6.5秒で、`--range` を付ければ特定のページだけを書き出せる<sup>1</sup>。エージェントは3回の確認で次のように直した。

| 回 | 見つかった問題 | 対応 |
|---|---|---|
| 1回目 | 本文の文字が小さく、余白が多すぎる。コードブロックが読めない。Mermaid 図が右端で切れる。カード見出しの末尾1文字だけが改行される | `style.css` で文字を大きくし、図の倍率を下げ、見出しを短くした |
| 2回目 | 図が小さくなりすぎた | 倍率を上げた（1.05 だと再びはみ出したので 0.88 にした） |
| 3回目 | 問題なし | ― |

情報量の上限を厳しくしたため、1回目は ppt-master とは逆に**スカスカ**になった。詰め込みの心配はなく、必要だったのは見た目の調整だけ。Mermaid 図の大きさだけは、倍率を何度か試す必要があった。

### フッターは slide-bottom.vue で付ける

左にデッキのタイトル、右に「6 / 12」のようなページ番号を出すフッターを、全スライドに付けた。表紙（`cover`）と最終ページ（`end`）には出さない。

全ページ共通のレイヤーなら `global-bottom.vue` が思いつくが、書き出したときにページ番号の状態がずれることがあると、公式リファレンスに注意書きがある<sup>3</sup>。そこで、スライドごとに描画される `slide-bottom.vue` と `$page` を使った。PNG・PDF・PPTX のいずれでもページ番号は正しく出て、`slides.md` には手を入れずに済んだ。

### pptx-editable の実際

Slidev v52.20.0 で入った編集可能な PPTX 出力も試した。

| 観察 | 内容 |
|---|---|
| クリック段階が別スライドになる | オプションなしだと、`v-clicks` やコードの段階ハイライトが1段階ごとに別スライドになり、12枚が22枚になった。`--with-clicks=false` を付けると12枚になる |
| 文字 | 見出し・箇条書き・コードは編集できるテキストになった |
| 表 | PowerPoint のネイティブの表ではなく、テキストボックスの集まりになった |
| 図 | Mermaid 図とアイコンは画像のまま（公式ドキュメントの記載どおり<sup>1</sup>） |
| フォント | 「Noto Sans JP」「JetBrains Mono」という名前で指定されるだけで、埋め込まれない。検証した Mac にはどちらも入っていないので、PowerPoint で開くと別のフォントに置き換わるはず（未確認） |
| 発表者ノート | 入っていた |

文字の修正くらいなら相手に頼めるが、表や図を直してもらうのは難しい。

## ppt-master での作り方

### ワークフロー全体で約28.5分

| 工程 | 時間 |
|---|---|
| 準備（venv、整合性チェック、プロジェクト作成） | 約1.3分 |
| 計画（2段階の確認、設計仕様書、デザインの固定値） | 約5分 |
| AI 画像生成の失敗と、計画の修正 | 約1.6分 |
| 執筆用リファレンスの読み込み、文字幅の較正 | 約4.8分 |
| 1〜5枚目の作成と中間チェック | 約4分 |
| 6〜14枚目の作成 | 約9分 |
| 最終チェック、修正、グラフ検証、発表者ノート | 約2.5分 |
| 書き出し | 約13秒 |

1ページずつ順番に作る設計なので、公式 FAQ の「10〜15ページで10〜20分」<sup>6</sup>に計画の時間が乗った形だ。

### 推奨をすべて採用しても、決めることが約25個ある

| 段階 | 内容 |
|---|---|
| 最初の確認 | 言語、聞き手、目的、持ち帰ってほしいこと、伝えたいこと、発表の場、発表後の使われ方、画面サイズ、自由デザインかテンプレートか、など約10項目 |
| 2回目の確認 | 3つのデザイン案から1つを選ぶ。各案に、構成パターン（5種）、見た目のスタイル（18種）、配色6色、書体、アイコン（4系統＋線の太さ）、画像の描き方（20種）の選択が含まれる |
| 制作設定 | 読み方のモード、ページ数の範囲、画像の入手方法、生成モード、仕様書レビューの有無、発表者ノート・アニメーション・ナレーションの有無など12項目 |
| 途中で追加 | 画像生成の失敗後の対応、グラフ・表をネイティブにするか、など3〜4回 |

テンプレート候補も44個（ブランド21、スタイル14、レイアウト7、デッキ2）登録されていた。今回は自由デザインで始めたので表示されなかった。事前に感じていた「選択肢が多すぎる」は、数えてみると本当に多かった。

採用されたのは、推奨の「結論先出し・スイスグリッド」案だった（ほかの2案は「ターミナル・ダーク」と「技術誌エディトリアル」）。白地に紺（#14325C）と朱（#E8552D）、游ゴシック＋Segoe UI、tabler の線画アイコン、読み方のモードは balanced（読む資料と発表の中間）。

### うまくいかなかったこと

- **AI 画像生成の失敗**: 推奨が「表紙画像を AI で生成」だったが、画像生成の API キーを設定していなかったので失敗した。ppt-master は計画の段階で認証情報を確認しない決まりなので、この環境では毎回同じ失敗が起こる。画像なしに切り替え、表紙の循環図はネイティブ図形で描き直した
- **ライブプレビューの失敗**: プレビュー用のサーバーは起動に失敗した
- **品質チェックでのはみ出し**: 最終チェックの1回目で、文字の枠からのはみ出しがエラー2件出た。文言を削るなどして直し、エラーも警告も0件になった
- **グラフと表**: `--native-charts-and-tables` なしで書き出したので、PowerPoint のネイティブのグラフ・表ではなく、編集できる図形の集まりになった<sup>7</sup>

### 出力の質は高い

- 14枚すべてがネイティブの図形と文字でできていて、画像は含まれない
- 右向きの矢印など、Office のプリセット図形を20個使っている
- 游ゴシックは Mac と Windows の両方に入っているので、PowerPoint で開いたときにフォントが置き換わりにくい
- 発表者ノートは全ページに入っていた

PPTX で相手に渡す前提なら、この出力はかなり強い。

## 数字で比べる

文字数は、書き出した PPTX の各スライドに含まれるテキストを数えた（フッターを含む）。

| 項目 | Slidev 版 | ppt-master 版 |
|---|---|---|
| 枚数 | 12枚（構成はこちらで決めた） | 14枚（ppt-master の計画に任せた） |
| 全体の文字数 | 約1,200字 | 約7,000字 |
| **1枚あたりの平均文字数** | **約100字** | **約500字** |
| 本文の多いページの文字数 | 約140〜210字 | 約410〜730字 |
| 作成時間 | 未計測（PNG 書き出しは12枚で約6.5秒） | 約28.5分 |
| 途中で決めること | `CLAUDE.md` のルールだけ | 約25項目＋途中の判断3〜4回 |
| PPTX の編集性 | 文字は編集可。表はテキストボックスの集まり、図とアイコンは画像 | すべてネイティブの図形と文字 |
| 日本語フォント | Noto Sans JP（名前で指定、埋め込みなし） | 游ゴシック（Mac と Windows の標準フォント） |

| 観点 | Slidev | ppt-master |
|---|---|---|
| 第一印象 | 素朴で余白が多い。AI っぽさがなく見やすい | 完成度が高く、プロが作った資料に見える |
| 情報量 | ルールどおり、1枚1メッセージ | 1枚に説明・注意・補足まで入り、読む資料の密度 |
| 図解 | Mermaid で必要なときだけ | 列の分割や矢印を多用する。構造は立派だが、口頭説明の助けになるとは限らない |
| 修正のしやすさ | Markdown を直してすぐ書き出せる。差分も Git で読める | ラベルを付けて指示すれば調整はしやすい。ただし再生成に時間がかかる |
| 見た目の統一 | `style.css` とフッター用の Vue ファイルを使い回せば毎回同じになる | 推奨デザインを毎回選び直す流れなので揃えにくい |

なお、両者のページ構成は別々に決めている。文字量の差には、情報量ルールの有無と構成の違いの両方が効いている。ppt-master は確認ゲートの設定次第で出力が大きく変わるので、あくまで「推奨設定のまま使った場合」の結果として読んでほしい。

## Slidev を選んだ理由

1. **詰め込みにならない**: 情報量は `CLAUDE.md` のルールで決まり、エージェントもそれに従う。ノートを暗記せず口頭で話すスタイルには、話のきっかけになる程度の量がちょうどいい
2. **速い**: 書き出しは数秒で、エージェントが見て直すループを何度も回せる
3. **表現力は十分**: Marp より表現の幅が広い（レイアウト、Vue コンポーネント、Mermaid、コードの段階ハイライトなど）。ppt-master ほど凝った見た目にはならないが、技術発表には足りる
4. **発表時間が読みやすい**: ppt-master のスライドでの発表が長くなりがちだったのは、1枚あたりの文字量が約5倍であることを考えると自然な結果だった

逆に、発表ではなく**読まれる資料**を作る場合や、PowerPoint で非エンジニアに渡して編集してもらう場合には、今でも ppt-master が有力だ。ネイティブ図形で作られ、游ゴシックで出力される点は、PPTX で渡すときに強い。

## 今後使う Slidev の雛形

今回の Slidev プロジェクトを、そのまま次回以降の雛形にした。

| ファイル | 役割 |
|---|---|
| `CLAUDE.md` | 情報量の上限、レイアウトの選び方、PNG での自己確認を必須にするルール |
| `style.css` | 文字サイズ、配色（ティール #0d9488）、カード、フッターの見た目 |
| `slide-bottom.vue` | タイトルとページ番号のフッター（表紙と最終ページには出さない） |
| `package.json` | `export:png`（自己確認用）、`export`（PDF）、`export:pptx`（`--with-clicks=false` 付き）のスクリプト |

`CLAUDE.md` には、上の情報量ルールに加えてレイアウトの選び方も書いてある。主張を1文で見せるなら `statement`、数字1つを強調するなら `fact`、2つを比べるなら `two-cols-header`、章の区切りは `section`。選択肢を5つに絞っておくと、エージェントが凝ったレイアウトを自作して崩す、ということが起きにくい。

## 残っている課題

- 両方の PPTX とも、PowerPoint で開いての表示は確認していない（確認用の画像は Chromium で描いたもの）
- Slidev の PPTX は、フォントを游ゴシックなど相手の環境にあるものに変えたほうが、PowerPoint で渡すときに崩れにくい
- ppt-master の読み方のモード presentation や、Create Template ルートで作る自分用テンプレートは試していない。これらで情報量や見た目の統一がどこまで改善するかは未検証

特に最後のものは、ppt-master の弱点をかなり潰せる可能性がある。試したらまた書く。

## まとめ

- Claude Code に同じ題材で Slidev と ppt-master のスライドを作らせたら、ppt-master（推奨設定のまま）は1枚あたりの文字量が約5倍、作成に約28.5分、決める項目が約25個だった
- ppt-master の見た目の完成度は高い。ただ、1枚に説明・注意・補足まで入るので、口頭で話す発表には情報量が多すぎる。発表が長引いていた理由はこれだった
- Slidev は `CLAUDE.md` に情報量の上限を書けばエージェントがそれに従い、PNG 書き出しが数秒なので作って見て直すループを何度も回せる
- 口頭で話す発表は Slidev、読まれる資料や PowerPoint で渡して編集してもらう資料は ppt-master、と使い分ける
