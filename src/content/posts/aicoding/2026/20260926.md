:::tip[要約]
* 半年前（2026年2月）は「人が書き、AIに部分的に直してもらう」前提で、**AI編集に最も向くのは Marp** という結論だった。いまはエージェントがスライドを丸ごと作り、PNG にレンダリングして自分で見て直すところまで回すのが普通になり、評価の前提が変わった
* **Markdown で技術スライドを作るなら、第一候補は Slidev に移った**。公式の Agent Skill・MCP サーバ・llms.txt がそろい、編集可能な PPTX（`--format pptx-editable`）も出せるようになった。Marp は軽くてトークン消費が少ない「軽量枠」になった
* **相手に編集可能な PowerPoint で渡すなら ppt-master が最有力**。SVG を経由してネイティブの図形を作る OSS で、見栄えとあとから直せることを両立している。ただしセットアップが重く、10〜15ページで10〜20分かかる
* 「PPTX に出せる」には**画像を貼っただけのものと、ネイティブで編集できるものの2種類**がある。Slidev の `pptx`、Marp の `--pptx`、Gemini Notebook の PPTX は前者
* うまくいっている人は、ツール選びより**スタイルガイド・レイアウト集・レンダリング確認ループの3点セット**を作ることに力を入れている
:::

Claude Code に「勉強会用のスライドを作って」と頼むと、とりあえず何かは出てくる。ただ、出てきたものが地味だったり、文字がはみ出していたり、PPTX で渡したら相手が1文字も直せなかったりする。どのツールを使わせるかで、このあたりの当たり外れがかなり変わる。

半年前にも一度、エンジニア向けのスライド作成ツールを比較した。そのときの結論は「AI で編集するなら Marp」だった。ところが、この7か月でツール側がエージェントに使われる前提で作られるようになり、結論が変わった。ここでは、Claude Code や Codex CLI などのエージェントと組むことを前提に、調べ直した結果をまとめる。数値（GitHub スター数・バージョン）は、特記がない限り 2026-09-26 時点のもの。

なお、候補のうち Slidev と ppt-master を同じ題材で実際に作り比べた話は、[別記事](/posts/aicoding/2026/20260927/)に分けた。

## 半年前の結論：人が書いてAIが直すなら Marp だった

2026年2月の時点では、対象を「人が Markdown を書き、ChatGPT や Cursor に部分的に直してもらう」使い方に置いていた。評価軸は Markdown の純度・学習コスト・AI に指示の出しやすさで、ランキングはこうなった。

| 順位 | ツール | 当時の評価 |
|---|---|---|
| 1 | Marp | 純粋な Markdown で完結し、「スライド3のコードを直して」がそのまま伝わる |
| 2 | Slidev | Markdown ベースで編集しやすいが、Vue コンポーネント部分は指示が複雑になる |
| 3 | reveal.js | HTML と Markdown が混在し、指示が複雑になりがち |
| 4 | MDX Deck | JSX が混ざり、React の知識も要る |
| 対象外 | Deckset、AI統合型ツール（Gamma など） | Deckset は GUI アプリなので自動化が困難。AI統合型は「AI が生成する」ツールで、「AI で編集する」用途とは別物 |

「人が主、AI が従」なら、この整理は今でもそれほど間違っていない。変わったのは、主従が逆転したことだ。

## この7か月で何が変わったか

| 変化 | 具体例 |
|---|---|
| ツールに公式 Skill・MCP が付くようになった | Slidev（Skill と MCP）<sup>2</sup><sup>3</sup>、Deckset（AI Slide Builder Skill）<sup>13</sup>、Gamma・Canva・Pitch（MCP）<sup>33</sup><sup>34</sup><sup>35</sup>、Google Slides MCP（Developer Preview）<sup>32</sup> |
| 編集可能な PPTX を作る手段が増えた | ppt-master<sup>16</sup>、Slidev `pptx-editable`<sup>1</sup>、open-slide<sup>12</sup>、PPTAgent<sup>25</sup>、Presenton<sup>26</sup> |
| レンダリングして目で確かめるループが標準になった | Anthropic pptx Skill（LibreOffice → PDF → 画像）<sup>20</sup>、ChatGPT・Codex のプレゼン機能<sup>24</sup>、Marp 実践記事の Playwright 検証<sup>37</sup> |
| 画像生成モデルでスライドを作る流れが出てきた | Gemini Notebook（旧 NotebookLM）の Slide Decks<sup>29</sup> |
| HTML で1枚ものの deck を作る Skill が人気になった | frontend-slides（約3万スター）<sup>27</sup>、guizang-ppt-skill（約2.7万スター）<sup>28</sup> |
| 古いツールの整理が進んだ | Fusuma はアーカイブ<sup>14</sup>、MDX Deck は実質停止<sup>15</sup>、Tome はスライド製品を終了<sup>45</sup> |

前回の対象外だった2つも立場が変わった。Deckset はコーディングエージェント向けの Skill を公式に配布していて、ソースは Markdown なのでエージェントから普通に扱える<sup>13</sup>。Gamma などの SaaS も API や MCP を出し、エージェントから呼べる部品になった。

## 評価軸を入れ替えた

Markdown の純度や学習コストはエージェントにとってあまり関係ない。代わりに、次の6つで見ることにした。

1. **ソースがテキストか**: エージェントが直接読み書きでき、Git で差分を取れるか
2. **ヘッドレスで自己検証できるか**: CLI で PNG や PDF にレンダリングし、エージェントが自分で見て直せるか
3. **公式の AI 連携があるか**: Agent Skill・MCP・llms.txt などが用意されているか
4. **PPTX にしたとき編集できるか**: 画像を貼っただけか、ネイティブの図形とテキストか
5. **再現性**: 同じ入力から同じ出力が得られるか、正本がクラウドにしかない状態になっていないか
6. **ライセンス・機密性**: AGPL やプロプライエタリの有無、データが外部に出るかどうか

特に2番目が効く。エージェントに作らせたスライドの品質は、「作る → 画像にする → 見る → 直す」のループを何回回せるかでほぼ決まる。このループを CLI 一発で組めるかどうかで、同じ Markdown 系でも差がつく。

## Markdown・コード系：第一候補は Slidev に移った

### Slidev：公式の AI 対応がいちばん厚い

v53.0.0（2026-09-16）、スター約4.9万。2025年11月から2026年9月までに約30回リリースしていて、非常に活発だ<sup>4</sup>。

- **公式 Agent Skill**: `npx skills add slidevjs/slidev` で入る。Claude Code のプラグインマーケットプレイスにも対応している<sup>2</sup>
- **組み込み MCP サーバ**（v52.17.0〜）: dev サーバ起動中は `http://localhost:<port>/__mcp` で使える。スライドの一覧・取得・更新・挿入・削除・移動・表示ページの切り替えができる。ただしスクリーンショットを撮るツールは含まれない<sup>3</sup>
- **llms.txt**: `https://sli.dev/llms.txt` がある<sup>2</sup>
- **自己検証**: `slidev export --format png --range N` で、指定したページだけをヘッドレスで PNG にできる<sup>1</sup>
- **PPTX 出力**: 従来の `--format pptx` はスライドを画像にして貼るだけで、テキストは選択できない。v52.20.0 で入った `--format pptx-editable` は、ブラウザ上の要素を測ってネイティブの図形・テキストとして組み直す。ただし SVG（Mermaid やアイコン）、KaTeX、CSS グラデーションなどは画像のまま残り、フォントは埋め込まれない<sup>1</sup>

弱みは、Node 22.12 以上と Playwright が必要なことと、凝ったレイアウトを作るには Vue と UnoCSS の知識が要ること。前回は「セットアップが重い」を減点にしたが、今はそのセットアップもエージェントがやってくれるので、実質的な負担はかなり下がった。

### Marp：軽くて書かせやすいが、AI 向けの機能は増えていない

marp-cli v4.5.1（2026-09-06）、スター約3,800<sup>5</sup>。

- 公式の AI 連携は、VS Code 拡張で入った「Copilot エージェントから export コマンドを呼べる」機能と、はみ出し警告（実験的・VS Code 内でのみ動作）くらい<sup>6</sup>。llms.txt はない。MCP や Skill はコミュニティ製のものがある
- `marp --images png` でページごとの PNG を出せるので、自己検証ループは組める
- `--pptx` は画像を貼るだけ。`--pptx-editable` は今も実験的で、LibreOffice が必要、発表者ノートは出せない。README 自身が「見た目を保ちたいなら勧めない」と書いている<sup>5</sup>

1ファイルの Markdown で完結し、トークン消費も小さい。この強みは半年前から変わっていない。ただ、エージェントに見た目まで任せると地味になりやすい（後述）。

### reveal.js：llms.txt に対応したが、検証ループは組みにくい

6.0.0（2026-03-11）で大きく刷新され、公式の React ラッパー、Vite ビルドへの移行、公式サイトの llms.txt 対応が入った。スター約7.2万<sup>7</sup>。一方で公式の CLI エクスポートがなく、PDF はブラウザで印刷するか、サードパーティの DeckTape を使う<sup>8</sup>。エージェントに自分で確認させるループを組むのが、Slidev や Marp より面倒だ。

### そのほかのフレームワーク

| ツール | 向いている場面 | メモ |
|---|---|---|
| Quarto | データ分析の発表 | R・Python・Julia のコードセルをその場で実行して図表を作れる。出力は revealjs・pptx・beamer<sup>9</sup> |
| Typst + Touying | 数式の多い発表・論文紹介 | `typst compile` で全ページを数ミリ秒で PNG にでき、確認ループが最速。PPTX は出せない<sup>10</sup> |
| presenterm | ターミナルで発表したい | コード実行、Mermaid・数式に対応。`--validate-overflows` ではみ出しを検出できる<sup>11</sup> |
| open-slide | 人の指摘をエージェントに渡したい | 2026年4月公開。1枚ごとに TSX を書く方式。ブラウザ上の要素にコメントを付けて `/apply-comments` で反映させるループが最初から組み込まれている。まだ若い<sup>12</sup> |

MDX Deck は npm の最終版が2020年で実質停止<sup>15</sup>、Fusuma は2024年12月にアーカイブ<sup>14</sup>、Remark も2020年から休眠している。前回比較に入れていたが、新しく採用するのは避けたほうがいい。

## PPTX を直接作るツール：編集可能性なら ppt-master

### ppt-master：見栄えと編集可能性を両立する OSS

PDF・DOCX・URL・Markdown などを材料に、**ネイティブ図形で編集できる PPTX** を作るワークフロー（Skill）<sup>16</sup>。MIT ライセンス。2025年12月に公開され、約9か月でスター約5.6万という異例の伸び方をしている。最新は v6.6.0（2026-09-19）で、ほぼ毎週リリースがある。

仕組みはこうだ<sup>17</sup><sup>19</sup>。

- AI が「制約付きの SVG」を書き、スクリプトがそれを DrawingML（PowerPoint のネイティブ形式）に変換する。SVG は ppt-master 専用の中間言語という位置づけ
- Strategist → Image_Generator → Executor と役割を切り替えながら、一つのエージェントが**1ページずつ順番に**作る。並列にしないのは、deck 全体の文脈を共有して見た目のブレを防ぐため
- 最初にデザイン仕様をユーザーに確認させる止めどころ（BLOCKING ゲート）がある

グラフや表は既定では「編集できる図形」として描かれ、`--native-charts-and-tables` を付けるとネイティブのチャートと表になる。Claude Code・Codex CLI・Cursor・Gemini CLI などで動き、FAQ では Claude を「推奨かつ最もテストされているモデル」としている<sup>18</sup>。

注意点も多い。

- Python 3.10 以上の環境が必要で、非エンジニアには敷居が高い
- 1ページずつ順に作るため、10〜15ページで10〜20分かかる。トークンも多く使う<sup>18</sup>
- 公式 FAQ 自身が「高品質な編集可能たたき台であって、完成品ではない」と書いている<sup>18</sup>
- 日本語フォントを指定しないと欧文フォントにフォールバックするという報告がある<sup>43</sup>
- PDF の読み込みに使う PyMuPDF は AGPL-3.0。社内ツールとして再配布するなら確認が要る<sup>16</sup>

### Anthropic pptx Skill：Claude 標準のやり方

新規作成は PptxGenJS のスクリプトを書き、既存 deck の編集は unzip して XML を直接いじる。検証はスキーマチェックと、LibreOffice で PDF にしてから画像にする目視 QA<sup>20</sup>。以前は HTML → PPTX（html2pptx）方式が中心だったが、2026年2月の PR #330 で PptxGenJS 中心に切り替わった<sup>22</sup>。「pptx Skill は html2pptx 方式」と書いている記事は古い情報だ。

手軽で、テンプレートへの流し込みにも強い。一方で「地味で文字の多いスライドになりがち」という評価も多い<sup>40</sup>。なお pptx などの Office 系 Skill は OSS ではなく source-available で、抽出や派生物の作成は禁止されている<sup>21</sup>。

### OpenAI Codex / ChatGPT のプレゼン機能

ChatGPT と Codex に、Google Slides と PowerPoint を作成・編集・プレビューする機能がある。スライド計画 → 構築 → レンダリングして検証、という流れで進む<sup>24</sup>。GitHub の `openai/skills` には一時期 `slides` Skill があったが、2026年4月に削除され、リポジトリ自体も deprecated になっている<sup>23</sup>。「Codex には slides Skill が組み込み済み」と書く記事もあるが、一次ソースでは確認できなかった。

### そのほか

研究発の PPTAgent は、HTML を書く → 画像にしてレビュー → 編集可能な PPTX に変換、という流れの Skill を Claude Code・Codex 向けに公開している<sup>25</sup>。Presenton は Gamma 的なサービスをセルフホストできる OSS で、Ollama などのローカル LLM も使えるので機密資料に向く<sup>26</sup>。

## HTML・画像生成系：見栄えと引き換えに何かを失う

見栄えを最優先するなら、HTML・CSS・JS で自由にデザインさせるのが強い。frontend-slides（MIT、約3万スター）は依存ゼロの単一 HTML を出し、3種類のスタイル見本から選ばせる<sup>27</sup>。ブラウザで開けばそのまま発表でき、GitHub Pages で公開しやすい。ただし PowerPoint で受け取りたい相手には向かない。guizang-ppt-skill など人気の HTML 系 Skill には AGPL-3.0 のものもあるので、社内で改変・配布するならライセンスを確認したほうがいい<sup>28</sup>。

画像生成モデルでページ全体を1枚の絵として作る方式は、さらに見栄えがいい代わりに**テキストが編集できない**。Gemini Notebook（旧 NotebookLM）の Slide Decks は無料で品質も高く PPTX も出せるが<sup>29</sup>、その PPTX は1枚ごとの画像で、文字は直せない<sup>30</sup>。要約資料の下書きには便利、という位置づけだ。

## SaaS も API・MCP で呼べる部品になった

前回は参考程度に並べただけだったが、多くが API や MCP を公開したので、エージェントから呼び出せる部品として見直した。主なものだけ挙げる。

| サービス | エージェントからの操作手段 | 補足 |
|---|---|---|
| Gamma | REST API、hosted MCP、Claude・ChatGPT コネクタ<sup>33</sup> | 連携はいちばん充実している。生成結果は毎回変わり、正本はクラウド側にある |
| Canva | AI Connector（MCP）<sup>34</sup> | ブランドテンプレートを使う機能は Enterprise 限定 |
| Pitch | MCP と API（2026年8月）<sup>35</sup> | テンプレートに変数を流し込む Deterministic モードがあり、再現性が高い |
| Google Slides | Slides MCP（Developer Preview、2026年7月〜）<sup>32</sup> | batchUpdate の JSON を残せば再現できる。Workspace の中で完結する |
| Claude for PowerPoint | PowerPoint アドイン（GA）<sup>31</sup> | スライドマスターやフォントを読み取って、テンプレートに沿って編集する |
| Microsoft 365 Copilot | PowerPoint Agent（2026年4月 GA）<sup>36</sup> | PowerPoint の中で完結する。外部から操作できる公開 API は見当たらなかった |

SaaS はデータが外に出る点だけは押さえておきたい。アカウント不要の MCP のように、生成した deck が共有 URL に残るサービスもあるので、機密資料には使わない。

## 素のまま任せると、Markdown 系は見た目で負ける

第三者の比較でいちばん分かりやすかったのが、Happycapy の「Skill Arena: Slides」だ<sup>41</sup>。Claude Sonnet 5 で3つの課題を作らせ、2人の審査員がブラインドで評価している（公開日と評価手順の詳細は不明）。

| Skill | スコア |
|---|---|
| frontend-slides | 8.2 |
| reveal.js | 8.0 |
| Anthropic pptx | 7.3 |
| MiniMax pptx-generator | 7.2 |
| Slidev | 5.0 |
| Marp | 3.8 |

見た目の点では、HTML やコードで書く方式が Markdown 系を上回った。一方でトークン消費は frontend-slides が約6.3万、Marp が約6,000で、**約10倍の開き**がある。

エージェント中心の作業では、ソースをエージェントが直接書けるテキスト形式がいちばん強く、Office ファイルが必要なときだけ PPTX ライブラリを使えばよい、という整理もある<sup>42</sup>。上のスコアは「素の状態で任せた場合」の評価で、次に書く仕組みを人が用意すれば Markdown 系の品質は大きく上がる。

## うまくいっている人はツールより仕組みを作っている

国内の実践記事を読むと、成功している人の共通点はツールではなく、スタイルガイド・レイアウトパターン集・レンダリング確認ループの3点セットだった。

```
リポジトリ構成の例
├── CLAUDE.md / AGENTS.md    # 作成ルール（1スライド1メッセージ、文字数上限など）
├── theme.css               # テーマ
├── layouts/                # レイアウトパターン集
├── .claude/skills/
│   ├── slide-create/       # 構成と本文の作成
│   ├── slide-review/       # 内容のレビュー
│   └── layout-fix/         # PNG にレンダリング → はみ出しを検出 → 修正
└── slides.md
```

- hirokidaichi 氏は、スタイルガイドと40種類のレイアウトパターンを用意したうえで、Playwright のスクリーンショットではみ出しを自動修正している。「人間が設計した仕組みの中でAIが動く形が現時点では最も効果的」とまとめている<sup>37</sup>
- Loglass の記事では、30種類以上のコンポーネントを持つ `theme.css` と、文字数やレイアウトの規則を検査するコマンドを用意し、スマホから GitHub 経由で Claude に作らせている<sup>38</sup>
- Insight Edge の記事は、PPTX 側で同じことをやっている。デザインはヘルパー関数の中に固定し、AI はどの関数にどのデータを渡すかだけを決める。11pt 以下の文字は例外を投げて止める。これで作業時間が約6割減ったという<sup>39</sup>

**AI にデザインさせるのをやめる**という方向に、Markdown 派も PPTX 派も収束しているのが面白い。

## よくある落とし穴

| 落とし穴 | 内容 | 対策 |
|---|---|---|
| はみ出し・レイアウト崩れ | ほぼすべての実践記事で報告されている | レイアウトの選択肢を絞る。PNG にして見させる。最小フォントサイズなどを機械的にチェックする<sup>37</sup><sup>39</sup> |
| ブラウザと PowerPoint の差 | HTML のプレビューでは問題なくても、PPTX にすると改行位置が変わる<sup>1</sup> | 最終形式でレンダリングして確認する（LibreOffice → PNG など）<sup>20</sup> |
| 「PPTX に出せる」の中身 | Slidev の `pptx`、Marp の `--pptx`、Gemini Notebook の PPTX は画像を貼っただけ<sup>1</sup><sup>5</sup><sup>30</sup> | 相手が編集するなら、ネイティブで出せるツール（ppt-master、pptx Skill、`pptx-editable`）を選ぶ |
| 日本語フォント | CI で PDF にすると豆腐（□）になる。PPTX はフォントを埋め込まないので、受け取った側で置き換わる | Noto Sans JP などを入れておく。游ゴシック・メイリオなど相手の環境にある和文フォントを明示する |
| 会社テンプレートを守らない | プロンプトの指示がテンプレートのフォントや色を上書きしてしまう<sup>44</sup> | マスターのプレースホルダーに流し込むか、デザインをコード側に固定する<sup>39</sup> |
| トークン消費 | HTML 系は Markdown 系の約10倍<sup>41</sup>。ppt-master は1ページずつ作るので遅い<sup>18</sup> | 構成は Markdown で固めてから清書に移る。大きな deck は分割して作る |
| 数字の捏造 | 存在しない統計値が紛れ込む<sup>44</sup> | 数値は元データから差し込む。レビュー用のサブエージェントに出典を照合させる |
| 機密データ | SaaS や匿名 MCP ではデータが外部に出る | ローカルで完結する OSS を使う。ただし ppt-master などもモデルの API にはデータを送る |

## 用途別のおすすめ

| 用途 | 第一候補 | 理由 |
|---|---|---|
| 勉強会・LT・技術登壇 | **Slidev** ＋ 公式 Skill ＋ MCP | 公式の AI 対応が厚く、`export --format png` で自己検証ループを組める。コードの段階ハイライトなど技術発表向けの機能も強い |
| 同上で軽さ優先 | Marp | トークン消費が一桁少なく済むこともある。見た目は theme.css とレイアウト集で補う |
| 非エンジニアに PPTX で渡す資料 | まず Anthropic pptx Skill か Codex、足りなければ **ppt-master** | ppt-master で編集可能なたたき台を作り、最後の仕上げは人が PowerPoint でやる |
| 同じ形式の資料を量産 | python-pptx / PptxGenJS ＋ デザイン固定のヘルパー関数 | AI にデザインさせず、データの流し込みだけを任せる<sup>39</sup> |
| 会社の公式テンプレート必須 | Claude for PowerPoint、Microsoft 365 Copilot | PowerPoint の中で完結するので、ガバナンスをかけやすい |
| 見栄え最優先の一回きりの発表 | frontend-slides、Gamma | PowerPoint で渡す必要がないなら HTML 系がいちばん映える |
| 数式の多い発表・論文紹介 | Typst + Touying、Quarto | Touying は確認ループが最速 |
| 機密情報を含む資料 | Slidev / Marp をローカルで、または Presenton ＋ ローカル LLM | データを外に出さない |

## Slidev と ppt-master は実際に作り比べた

表の上では、技術登壇なら Slidev、編集可能な PPTX なら ppt-master になる。ただ、机上の比較だけでは「エージェントに任せたとき、どんなスライドが出てくるか」は分からない。そこで、この記事の元になった調査資料を題材に、両方で勉強会用の要約スライドを作ってみた。

結果として、ppt-master は推奨設定のままだと1枚あたりの文字量が Slidev 版の約5倍になり、自分の発表スタイルには Slidev のほうが合っていた。詳しくは[こちらの記事](/posts/aicoding/2026/20260927/)に書いた。

## まとめ

- 半年前は「人が書いて AI が直す」前提で Marp を推していた。エージェントがスライドを丸ごと作り、自分で見て直す時代になって、前提が変わった
- Markdown の第一候補は **Slidev** に移った。公式 Skill・MCP・llms.txt・`pptx-editable` がそろい、PNG での自己検証も CLI 一発でできる。Marp は軽量・低コスト枠になった
- 編集可能な PowerPoint が必要なら **ppt-master**。ただし重く、遅く、あくまでたたき台
- 「PPTX に出せる」は、画像を貼っただけのものとネイティブで編集できるものを区別して見る
- どのツールを選んでも、品質を分けるのはスタイルガイド・レイアウト集・レンダリング確認ループの3点セット

この分野は変化が速い。ppt-master は毎週リリースがあり、Slidev もこの1か月でメジャーバージョンが上がっている。導入前には公式ページで最新の状態を確認してほしい。
