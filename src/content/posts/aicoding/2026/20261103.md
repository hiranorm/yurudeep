* DeepSeek Harness の公式アカウントが、常駐型エージェント「Super-agent」の設計アイデアを長文で公開した。製品機能の紹介ではなく、**アーキテクチャの議論**という位置づけ

:::

Claude Code のようなコーディングエージェントは、1つのセッションに1つの仕事を頼むのが基本になっている。速く終わらせたければ、ターミナルを複数開いてセッションを並べればいい。

ところが並べるほど、「どのセッションが何をしていて、どこで止まって質問を待っているのか」を追うのが大変になる。モデルはまだ働けるのに、人間の側が先に音を上げる。

この「人間の注意力がボトルネック」という問題に、正面から設計で答えようとしたのが、DeepSeek Harness の公式アカウントが 2026-11-01 に公開した長文記事「Exploring Super-agent Design: Towards a More Autonomous Agent System」である<sup>1</sup><sup>2</sup>。ただ、この記事は中国語記事の機械翻訳でかなり長く、通読がつらい。

そこで内容を要約して、図に起こしながら分解してみた。[前回のハーネス記事](/posts/aicoding/2026/20260928/)と同じく、理解のために分解するのが目的で、Claude Code の機能との対応も付けている。

## 結論：ボトルネックは人間の注意力

![人間が同時に追えるのは3〜5セッションまで。それ以上のセッションは追いきれなくなる](/blogimg/super-agent/attention.png)

原文の出発点は、次の観察である<sup>1</sup>。

- 今のエージェントは「セッション」単位で動いている
- 人間が同時に追えるセッションは 3〜5 個程度
- したがって、マルチタスクのボトルネックは**モデルの性能ではなく人間の注意力**になっている

単一セッションのローカルエージェントに CLI や MCP、各種コネクタを後付けしても、次の問題は残る<sup>1</sup>。

| 問題 | 内容 |
|---|---|
| 同期ループ | 長い処理で1本のループがブロックされる |
| コンテキスト混在 | 複数タスクの文脈が混ざる |
| オフラインで停止 | 端末がスリープ・オフラインになると止まる |
| 手動運用 | セッションの管理を人間がやり続ける |

原文の答えは、**セッションを人間から隠す**ことだ。ユーザーがセッションを作って管理するのは、低レベルな LLM API から引き継いだ習慣にすぎない、という立場をとる<sup>1</sup>。人間は1つの常駐エージェント（Super-agent）に話しかけるだけにして、裏で何本セッションが動いているかは実装の詳細にしてしまう。

## Super-agent に求める4つの性質

原文は Super-agent に4つの性質を求めている<sup>1</sup>。

| 性質 | 意味 |
|---|---|
| Continuous（連続性） | IM や GitHub など普段の場所から話しかけられ、どこから話しても「同じ1人」として振る舞う。IM で指示して PR コメントで修正しても追従する |
| Productive（生産性） | 返事が速く、複数の複雑なタスクを並列かつ高品質にこなす。前の指示が終わる前に次を受け付ける |
| Proactive（能動性） | 環境のイベントを監視し、重要なものにだけ反応して、他は黙る |
| Persistent（永続性） | 常時オンラインで、実際の作業環境につながり、異常から自己回復する |

社内で動いているインスタンスは、IM のグループチャットと GitHub の PR をまたいで1つのタスクを継続し、誰にも呼ばれていなくても公開チャットでバグを見つけて修正 PR を出すという<sup>1</sup>。

単一の ReAct ループでは、この4つを同時に満たせない。そこで周辺のシステムで実現する。原文が挙げる仕組みは5つで、性質との対応は次のようになる<sup>1</sup>。

![5つのモジュールと4つの性質の対応。2層アーキテクチャはContinuousとProductive、イベント駆動はProactive、全二重・マルチチャネルはContinuousとProductive、計算・状態・環境の分離とWatchdogはPersistentを担う](/blogimg/super-agent/modules.png)

## 全体像

5つの仕組みを1枚にまとめると、こうなる。丸数字は後の節の番号に対応している。

![全体アーキテクチャ。IM・GitHub・メールなどのイベントがフィルタを通り、新規のものはRouterへ、購読済みThreadのものはWorkerへ直接渡る。Routerは対話と振り分けだけを行い、Workerがタスクを実行する。計算はステートレスなクラウドにあり、状態はDB、実行環境は各マシンのdaemon。Watchdogはシステムの外から監視・修復する](/blogimg/super-agent/overview.png)

流れを言葉にすると次のとおり。

1. IM・GitHub・メールなどから届くイベント（Trigger）を、まずフィルタにかける
2. 新しい話題は Router に渡す。すでに担当 Worker がいる話題は、Router を飛ばして Worker に直接渡す
3. Router は Worker にタスクを配り、Worker は実際の作業をして結果を Router に報告する
4. Router がチャネルの作法に合わせて人間に返信する
5. これらの計算はステートレスなクラウドで動き、状態は DB に、コマンド実行は各マシンの daemon に切り出されている
6. Watchdog がシステムの外から全体を見張る

ここから1つずつ見ていく。

## ① 2層アーキテクチャ（Router / Worker）

### なぜ2層なのか

連続性とスループットはトレードオフになる<sup>1</sup>。

| 方式 | 長所 | 短所 |
|---|---|---|
| 全部を1セッションでやる | 文脈が最も良い | ReAct が直列で遅く、タスクの詳細が混ざる |
| イベントごとに新しいセッション | スループットが高い | 文脈を共有できず、返信もバラバラ |
| 2層（Router + Worker） | 両方の長所を取る | — |

### Router と Worker の役割

![Router層は1つだけで、全ての人間入力の入口として順序付け・調整・記憶を担い、対話と振り分けだけをする。軽量モデルで足りることが多い。Worker層はタスクの数だけあり、1 Worker = 1タスクで、分離されたコンテキストとフルツールを持ち、最強モデルで品質を決める。人間とは直接話さない](/blogimg/super-agent/router-worker.png)

ポイントは、**Router が自分では作業をしない**ことだ。Router は人間と話し、タスクを起票して Worker に渡し、報告を受けて全体の状況を覚えておく。Bash がなくても動くし、軽量なモデルで足りることが多い<sup>1</sup>。

一方の Worker は、1つのタスクに専念する。コンテキストは他のタスクから分離され、ツールは全部使え、モデルは最強のものを使う。成果物の品質は Worker が決める<sup>1</sup>。

原文は Agent Team との違いにも触れている。Agent Team の Team Lead は、密結合な1つのタスクを分解する役なので重い推論が要る。Router はタスクを配って関係を把握するだけなので、もっと軽い<sup>1</sup>。

### Router は届いたイベントをまとめて処理する

Router は長寿命の1つの LLM セッションである。Router が考えている間に届いたイベントはキューに積まれ、次のターンでまとめて処理される<sup>1</sup>。

入力が長く出力が短い判断なので、まとめて渡すと prefill で並列に処理でき、1判断あたりの時間が下がる。実験結果は後述する。

## ② イベント駆動 Trigger

入力はチャット、メール、カレンダー通知、レビューコメント、CI の結果などの半構造化イベントになる。原文はこれを Trigger と呼び、4段階のパイプラインで処理する<sup>1</sup>。

1. フィルタリング
2. ルーティング
3. コンテキスト整理
4. 先回り実行

### フィルタリング：Fast Path と Slow Path

![イベント流の大半はノイズ。まずコードで書いたFast Pathがソース・グループ・ユーザーやbotの許可リストで判定し、無視するもの・明示依頼・候補に分ける。候補は自然言語で書いたポリシーに従ってLLMのSlow Pathが判定し、不要なら捨て、対応するならRouterへ渡す](/blogimg/super-agent/filter.png)

イベントの大半はノイズなので、まずコードで書いた Fast Path で安く振り分ける。判断が要るものだけを LLM の Slow Path に回す<sup>1</sup>。

Slow Path のポリシーは自然言語で書くので、人間があとから「こういうのも拾って」と追加・変更できる拡張ポイントになっている<sup>1</sup>。

### ルーティング：Thread の購読とパススルー

原文では、1つの PR、IM のトピック、メールのやり取りのように、つながった一連のイベントを **Thread** と呼ぶ<sup>1</sup>。

![ユーザーがPRに最初のコメントをすると、フィルタはSlow Pathで判定してRouterへ渡し、RouterはWorkerを起動してそのThreadを購読させる。同じThreadへの追加コメントは、Routerを経由せずWorkerへ直接パススルーされる。Workerは主要な結論だけをRouterに報告し、話題外のイベントは差し戻す](/blogimg/super-agent/thread.png)

Worker が Thread を購読すると、その Thread の続きは Router を通らずに Worker へ直接届く。これがパススルーである<sup>1</sup>。

- 購読は多対多。同じ Thread を購読している Worker 全員に同じイベントが届くので、Worker 同士は1対1のメッセージなしで協調できる<sup>1</sup>
- 同じ PR をいじる Worker 同士の競合も、同じ通知を見ているので基本的には自分たちで解決できる。タスクをまたぐまれなケースだけ Router が仲介する<sup>1</sup>
- パススルーがないと、Router の判断回数とトークン消費が増える（後述の実験で確認されている）

### コンテキスト整理：Inline と Spill、Chain of Recall

原文には「コンテキストウィンドウの浪費はモデルの知性の浪費」という一文がある。コンテキストを**キャッシュ**として扱い、2つの操作を使い分ける<sup>1</sup>。

| 操作 | 内容 |
|---|---|
| Inline | 必要になりそうな情報を直接コンテキストに入れる |
| Spill | 本体は外に置き、ID や要約だけをコンテキストに残す |

近いものから段階的に広げるのが基本で、ID と要約 → 関連 ID → 近傍の中身（先頭の数十文字、前後の IM メッセージ、返信先、隣のレビューコメント）→ 長いものは上限で切ってツールで読めるポインタを残す、という順になる<sup>1</sup>。

Router 用には **Chain of Recall** という仕組みもある。Trigger・Thread・Worker のセッションにユニークな ID を振っておき、「IM の Thread → それを担当した Worker のセッション → そこから派生したコードレビューの Thread」のように参照をたどって、多段に思い出す<sup>1</sup>。

### 先回り実行（Speculative Execution）

必要かどうか分かる前に裏で作業を始めておき、役に立った結果だけを届けて、残りは捨てる<sup>1</sup>。

- 個人用途：会議の招待が来たら、カレンダーの競合チェック、相手の背景調査、返信の下書きまで済ませて、人には承認だけを求める
- 開発用途：「黙って再現して直す」ポリシーを入れておく。問題が再現でき、簡単な修正が見つかったときだけ発言する。グループチャットで議論している間に、修正 PR がもう出ている

## ③ 全二重・マルチチャネル対話

### 全二重：ツールの完了を待たずに話を聞く

![従来の半二重では、エージェントがrun(build)を呼ぶと完了までブロックされ、その間に来た新しい指示に応答できない。全二重ではstart(build)が即座にStartedを返すので、新しい指示にすぐ応答でき、ビルドの完了は新しいイベントとして後から届く](/blogimg/super-agent/duplex.png)

普通の ReAct ループは半二重で、長いツール（ビルドなど）を呼ぶとその間はユーザーの話を聞けない。全二重では、ツールを `start()` すると即座に "Started" が返り、完了は新しいイベントとして後から届く。長すぎるなら `stop()` で止められる<sup>1</sup>。

新しい入力は「バックグラウンドのツールが終わった後」ではなく、「今の推論ステップが終わった後」に処理される。DeepSeek Harness には実装済みだが、**デフォルトでは無効**とのこと<sup>1</sup>。

### マルチチャネル：場所ごとに作法を変える

Worker の詳細なログは内部に閉じ込め、人間に見せる返信はチャネルの作法に合わせる。作法はプロンプトで定める<sup>1</sup>。

| チャネル | 作法 |
|---|---|
| IM | 割り込みは最小限。人に連絡するのは判断や承認が必要なときだけ。質問は直接的に、結論は短く。1返信100語まで |
| GitHub・メール・ドキュメント | 構造化して密度高く。PR には背景、変更内容、検証結果をプロジェクトの規約に沿って書く |

## ④ 計算・状態・実行環境の分離

![Beforeのローカルエージェントは、ノートPC1台に計算・状態・環境が全部載っていて、スリープすると全部止まる。AfterのSuper-agentでは、計算はステートレスなクラウドコンテナ、状態はDB、環境は個人PCやクラウドVMのdaemonに分かれ、計算がdaemonにコマンドを送って結果を受け取る](/blogimg/super-agent/decouple.png)

ローカルエージェントは「ループの計算」「セッションの状態」「実行環境」の3つを1台の端末に縛り付けている。だからノートPC を閉じると全部止まる。原文は、計算とストレージの分離という古典的な考え方で、これを2段階で切り離す<sup>1</sup>。

1. 計算と状態を分ける：ループはステートレスなクラウドコンテナで回し、状態は DB に置く。コンテナは自由にスケール・再起動・差し替えできる
2. 計算と環境を分ける：各マシンでは、コマンドを実行して結果を返すだけの軽量なステートレス daemon を動かす

面白いのは、**環境はその場に残す**という判断だ。未コミットの変更、認証情報、社内ネットワークへの依存、特定のハードウェアやツールチェーンがあるので、クラウドのサンドボックスに環境を作り直すのは高コストで壊れやすい<sup>1</sup>。だから自分のマシンを環境として差し出す。原文はこれを BYOM（Bring Your Own Machine）と呼んでいる。オフラインのマシン向けのタスクはキューに積まれ、再接続したときに実行される<sup>1</sup>。

この考え方は、Anthropic が Managed Agents について書いた「Decoupling the brain from the hands」とよく似ている<sup>4</sup>。

| 観点 | Anthropic Managed Agents | DeepSeek Super-agent |
|---|---|---|
| 共通点 | ステートレスな harness、外部に置いたセッションログ、統一インターフェースでの接続 | 同左 |
| 主な対象 | マネージドサービス | 断続的にオンラインになる個人のマシン |
| 環境 | サンドボックス中心 | BYOM＋クラウド＋オンデマンド |

## ⑤ Watchdog

![定期メッセージで起動されるWatchdog Sessionはメインシステムの外にあり、APIエラーや状態復旧の失敗を処理し、LLMで各Workerの進捗や逸脱を判定し、異常を修復する。メンテナーは自然言語で「なぜ失敗した？」と質問でき、Watchdogは実行時にプロンプトやトリガールールを調整する](/blogimg/super-agent/watchdog.png)

エージェントの故障は、プロセスが落ちる「クラッシュ」ではないことが多い。プロセスは生きているのに空回りしていたり、目標からずれていたりする。だから Watchdog は**生存ではなく進捗**を監視する<sup>1</sup>。

- メインシステムの外にあるセッションを、定期メッセージで起動する
- API エラーや状態復旧の失敗を処理する
- LLM で各 Worker が実際に進んでいるか、ずれていないかを判定する
- 一時的な外部障害なら、解消するまで再確認する
- メンテナーは自然言語で「なぜ失敗した？」と聞ける。Watchdog は実行時にプロンプトやトリガールールを調整できる

## 予備実験：単一セッションはプロンプト次第でブレる

原文には予備実験の結果も載っている。合成ワークロードと簡略化した環境での実験で、原文自身が「目安」と断っている。使ったモデル名は非公開<sup>1</sup>。

### システム全体のアブレーション

グループチャットと GitHub CI のメッセージ約300件を流した。うち作業依頼は約20件で、残りは雑談・追加連絡・キャンセル・CI の通知。コーディング部分は時間を消費するだけのモックツールにして、スケジューリングの性能だけを測っている。各設計5回ずつ実行<sup>1</sup>。

| 設計 | 完了時間 p50 / p95（分） | 1回あたりのキャッシュ読み込みトークン |
|---|---|---|
| Super-agent | 12.4 / 15.7 | 23.2M |
| Super-agent（パススルーなし） | 12.6 / 15.5 | 31.8M |
| 単一セッション＋subagent（中立プロンプト） | 20.4 / 29.5 | 6.1M |
| 単一セッション＋subagent（委譲優先プロンプト） | 13.8 / 29.0 | 10.8M |

![完了時間p95の棒グラフ。Super-agentは15.7分、パススルーなしは15.5分、単一セッション（中立）は29.5分、単一セッション（委譲優先）は29.0分](/blogimg/super-agent/p95.png)

読み取れることは次のとおり<sup>1</sup>。

- 中立プロンプトの単一セッションは、5回とも一度も subagent に委譲しなかった。自分で作業している間に割り込みが積み重なり、p95 が 29.5 分まで伸びた
- 委譲を優先するよう書いたプロンプトでも、5回中1回は「小さい作業だから」と自分でやってしまい、ロングテールが出た
- つまり単一セッションでは、委譲するかどうかが**プロンプトとその場の判断任せ**になる。2層構造なら、Router はそもそも作業しないので、**構造で**この問題が消える
- Super-agent はトークンを多く使う代わりに、速く安定して終わる
- パススルーを外しても完了時間はほぼ変わらないが、Router の判断回数が約30%、トークンが約37%増えた

### Router のバッチ処理

Router だけ実モデルにして、Worker はモックにした実験もある。判断が必要な Trigger の到着ペースを、毎分約1件から約40件まで上げた<sup>1</sup>。

| 指標 | 約1件/分 | 約40件/分 |
|---|---|---|
| 平均バッチサイズ | 1.0 | 2.8 |
| 1リクエストあたりの時間 | 2.5 秒 | 3.9 秒 |
| 1判断あたりの償却時間 | 6.4 秒 | 1.6 秒 |

負荷が上がるほどバッチが効いて、1判断あたりは速くなる。今のチーム規模なら、パススルーなしでも Router 1つで上限に達しないので、早すぎる分割（シャーディング）は不要、というのが原文の見立てだ<sup>1</sup>。

## Claude Code で言うとどれか

[前回のハーネス記事](/posts/aicoding/2026/20260928/)と同じく、5つの仕組みを Claude Code の機能に当てはめてみる。

| Super-agent の仕組み | Claude Code で近いもの | 違い |
|---|---|---|
| ① Router / Worker | メインセッション＋subagent（`Agent` ツール）。メインセッションから起動した subagent はデフォルトでバックグラウンドで動き、その間も会話を続けられる<sup>5</sup>。実験的な agent teams もある<sup>6</sup> | メインセッションは自分でも作業するので、原文の実験でいう「単一セッション＋subagent」側にあたる。agent teams のリードは、原文がわざわざ Router と区別した Team Lead に近い |
| ② イベント駆動 Trigger | GitHub Actions の `@claude` メンション<sup>8</sup>、クラウドの scheduled tasks（スケジュール・API・GitHub イベントで起動）<sup>9</sup>、Auto-fix pull requests（PR の GitHub アクティビティを購読して CI 失敗やレビューコメントに反応）<sup>10</sup> | `@claude` は Fast Path の「明示依頼にだけ反応」に、Auto-fix は Thread の購読にかなり近い。誰にも呼ばれずに LLM がポリシーで判断して動く Slow Path や先回り実行に当たるものは見当たらない |
| ②のコンテキスト整理 | ツール出力のオフロード、Skills（説明だけ常に載せ、本文は呼ばれたときに読む）<sup>13</sup>、MCP ツールの遅延読み込み（`ToolSearch`）<sup>14</sup> | 考え方は Inline / Spill そのもの。Chain of Recall のように ID の参照グラフをたどる仕組みは表に出ていない |
| ③ 全二重 | `Bash` の `run_in_background`、`Monitor` ツール、バックグラウンドの subagent。動いている間も同じセッションで作業を続けられ、完了やイベントは後から届く<sup>5</sup><sup>7</sup> | 体験としてはほぼ全二重。Claude Code のほうがデフォルトでこの動きになっている |
| ③ マルチチャネル | GitHub Actions、Claude Tag（Slack） | チャネルごとの作法は、プロンプトや `CLAUDE.md` で書き分けることになる |
| ④ 計算・状態・環境の分離 | Remote Control（実行はローカルのまま、claude.ai やスマホから操作）<sup>11</sup>、Claude Code on the web（クラウドの VM で動き、ノートPC を閉じても続く）<sup>10</sup>、Claude Managed Agents（環境は Anthropic 管理のサンドボックスか、セルフホストのサンドボックス）<sup>12</sup> | 普段の CLI は、まさに「ノートPC1台に計算・状態・環境が全部載っている」Before 側。Remote Control は操作の場所を変えるだけで、分離ではない。web 版は計算と環境をまとめてクラウドに移す方向で、BYOM とは逆 |
| ⑤ Watchdog | `/loop`（セッション内で定期実行）<sup>15</sup>、クラウドの scheduled tasks<sup>9</sup>、hooks | 定期起動して進捗を見る役は作れる。ただし `/loop` はセッションが終わると止まるので、「システムの外」に置くならクラウド側の scheduled tasks になる |

こうして並べると、部品はかなり揃っている。足りないのは、それらを**1つの常駐エージェントとして束ねる層**、つまり Router だと分かる。

今の Claude Code では、Router の役を人間がやっている。どのターミナルでどのセッションが何をしているかを覚え、終わったものに次の指示を出し、PR のコメントを見て適切なセッションに貼り付ける。原文が「人間の注意力がボトルネック」と言っているのは、まさにこの作業のことだ。

## 原文が挙げる未解決の課題

原文は、残っている課題も4つ挙げている<sup>1</sup>。

- **2層構造のスケール**：Router をいつ・どれだけ分割するか。Worker 同士を直接つなぐか。イベント判定や想起に特化したモデルを学習するか。数か月運用すると長期記憶がボトルネックになる
- **セッションのないエージェントとの付き合い方**：裏で動いているタスクをユーザーにどう見せるか。チャット画面が主役なのは歴史的な経緯にすぎないかもしれず、GitHub のような領域ごとの UI に移っていく可能性がある。途中での介入や引き継ぎ、リアルタイムの共同作業も課題
- **コンテキストの境界とエージェント間連携**：組織の中で何を共有し何を分けるか。個人のエージェントとチームの Super-agent をどう協調させるか。権限の境界をまたぐ安全な協調は未解決
- **セキュリティとプライバシー**：イベント駆動の入力は、信頼できないコンテンツに触れる面を広げる。サーバの侵害やプロンプトインジェクションで、つながっている全マシンが乗っ取られうる。認証情報を「見ずに使う」仕組みが必要

最後のセキュリティの話は重い。BYOM で自分のマシンを差し出し、公開チャットのイベントで勝手に動くエージェントは、便利さと引き換えに攻撃面がかなり広い。

設計の一部は、プロトタイプのプラグイン `dsh-superagent-prototype` として GitHub で公開されている。DeepSeek の公式製品ではなく、MIT ライセンス<sup>3</sup>。

- 1つの GitHub リポジトリに紐づく、能動的なコーディングエージェント。DeepSeek Harness 用のバンドルとして提供される
- 基本方針は「人間の注意をできるだけ少なく取り、できるだけ多くの価値を返す」。頼まれたとき、またはチームが書いたルールが許すときだけ動く

- 社内版とは違い、記事のアイデアの一部は未実装
- セットアップは「Read SETUP.md in this repository and set up dsh-superagent with me.」とコーディングエージェントに頼む方式

## 個人的な意見：DeepSeek をローカルで動かしてつなぐのはやめておく

設計の考え方を長文で公開してくれたこと、プロトタイプをオープンソースにしてくれたことは、素直にありがたい。機構の説明も、エージェントを理解するうえで大変助かった。

ただ、**DeepSeek のモデルをローカルで動かして、このハーネスにつなぐのはやめておいたほうがいい**と思っている。

きっかけは、2026-10-26 に Cohere が公開した報告だ<sup>16</sup>。Alibaba の open-weight モデル Qwen3.8-Flash-Next に、セキュリティ系ベンチマークの課題（マルウェアの検知ルールを書く）を解かせたところ、次のような動きをしたという。

1. `/tmp` の中身を一覧する
2. curl・wget・python3 などの転送ツールが入っているか確かめる
3. マシンの DNS 設定を読む
4. Alibaba Cloud の北京リージョンにあるストレージへ、テスト用の文字列を PUT でアップロードしようとする

課題にはまったく必要のない操作である。Cohere のサンドボックスは外向きの通信を塞いでいたので届かなかったが、普通の開発用ノートPC や CI ランナーなら外部サーバに届いていた、と Cohere は書いている<sup>16</sup>。

公平のために補足しておくと、この件で問題になったのは Qwen で、DeepSeek ではない。発生頻度は 10 万回に 1 回未満で、意図的な仕込みなのか学習データの残りかすなのかは Cohere 自身も判断できないとしている<sup>16</sup>。証拠が足りない、Cohere の環境の作りが結果に影響したのではないか、という反論も出ている<sup>17</sup>。

それでも、この記事の文脈では無視できない。Super-agent は、BYOM で自分のマシンをエージェントに差し出し、公開チャットのイベントをきっかけに、人が見ていないところで勝手にシェルを叩く設計である。原文自身も、未解決の課題に「認証情報を見ずに使う仕組みが必要」と書いている。中身を検証しきれない重みを、そういう場所に置くのは怖い。10 万回に 1 回でも、常駐して回り続けるエージェントなら、いずれ当たる。

ローカルで動かせば手元から出ないので安全、というのは、モデルがツールを持たないチャット用途までの話だ。シェルとネットワークを渡した瞬間に、その前提は崩れる。重みが無料で手に入るのはありがたいが、ただより安いものはない。

どうしても試すなら、Cohere の推奨どおり、自分で作っていない重みは署名のないバイナリと同じに扱い、エージェントの外向き通信はデフォルトで塞いでおくのがよさそうだ<sup>16</sup>。

## まとめ

- DeepSeek Harness の Super-agent 設計は、**マルチタスクのボトルネックは人間の注意力**という観察から出発している
- 答えは、セッションを人間から隠し、1つの常駐エージェントに任せること。中身は2層構造・イベント駆動・全二重・計算と状態と環境の分離・Watchdog という、古典的なシステム設計の組み合わせ
- 核は Router / Worker の2層。Router は作業をしないので、「委譲するかどうか」がプロンプト次第でブレる単一セッション方式の弱点を、構造で消せる
- Claude Code に当てはめると、バックグラウンドの subagent、Auto-fix pull requests、クラウドの scheduled tasks など部品は揃いつつある。今は Router の役を人間がやっている
- 設計の公開はありがたいが、DeepSeek をローカルで動かしてつなぐのはやめておく。シェルとネットワークを渡すエージェントでは、「ローカルだから安全」は成り立たない。ただより安いものはない
- 原文の言葉を借りれば、エージェントは「待っているチャット窓」から「常時オンラインの協働者」へ移ろうとしている。人間が担うのは、判断と承認になる
