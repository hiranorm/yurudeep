## きっかけ：イルカのソナー通信が描けない

このブログのアイキャッチは、2026 年 4 月から FLUX.1-schnell で作ってきた。Apache 2.0 で商用利用でき<sup>1</sup>、Google Colab の GPU で 1 枚 20 秒台で出る。深海生物にテーマ語を掛け合わせた絵（ダイオウイカのハーネス、マリンスノーのトークンなど）は、だいたいこれで足りていた。

うまくいかなかったのが、[全二重音声 AI の記事](/posts/deeplearning/2026/20261117/) 用の「イルカがソナーで通信する」絵である。プロンプトはこう書いた。

```text
two dolphins exchanging glowing sound waves, small floating icons (document, code bracket,
chat bubble) traveling along the wave rings, deep sea, bioluminescent, clean illustration
```

出てきたのがこれ。

![FLUX.1-schnell で生成した2頭のイルカ。足元に水面の波紋のような輪があり、頭上に小さなアイコンが2つ浮いている](/blogimg/eyecatch/dolphin_sonar_message.webp)

かわいいが、狙いとは違う。気になったのは次の 3 点である。

1. 音波のリングが描けていない。2 頭の間を流れるはずの光る輪が、足元の水面の波紋になっている
2. アイコンが音波に乗らない。小さいのが 2 つ浮いているだけで、運ばれている感じがない
3. 構図が毎回似る。プロンプトを 6 種類書き分けても、2 頭の向かい合いになりがち

schnell の公開は 2024 年 8 月で、もう 2 年以上前のモデルになる。乗り換え先を調べることにした。

## Apache 2.0 で使える画像生成モデル（2026 年 11 月時点）

条件は「ローカル（Colab）で動く」「広告付きのブログで使ってよい」の 2 つ。広告やアフィリエイトがあるブログは、ライセンス上は商用と考えるのが安全である。たとえば Krea 2 のライセンスは、商用利用を「直接・間接に収益を生むこと」と定義している<sup>9</sup>。

Apache 2.0 か MIT で、現実的な候補は次のとおり。

| モデル | 規模 | ライセンス | ステップ数 | 公式カードの特徴 |
|---|---|---|---|---|
| FLUX.1-schnell（現行） | 12B | Apache 2.0<sup>1</sup> | 1〜4 | — |
| FLUX.2 [klein] 4B | 4B | Apache 2.0<sup>2</sup> | 4 | 約 13GB の VRAM で動く |
| Z-Image-Turbo | 6B | Apache 2.0<sup>3</sup> | 9（DiT 8 回） | 写実と中英テキスト描画が得意 |
| Z-Image（base） | 6B | Apache 2.0<sup>4</sup> | 28〜50 | アニメ・スタイライズドイラストまで扱え、出力の多様性が高い |
| HiDream-O1-Image | 8B | MIT<sup>5</sup> | 28〜50 | 写実中心。専用リポジトリで動かす |
| Qwen-Image-2512 | 20B | Apache 2.0<sup>6</sup> | — | 写実寄り。重い |

意外だったのは、リーダーボード上位のオープンウェイトモデルの多くが、非商用か条件付きだったことである<sup>7</sup>。FLUX 3 Image Klein は年商 500 万ドル未満なら商用無料<sup>8</sup>、Krea 2 は年商 100 万ドル未満なら商用可だが、コンテンツフィルタの実装が義務で、30 日前の通知でライセンスを打ち切れる<sup>9</sup>。新しいモデルほどライセンスが緩いわけではない。

「パステルに強い」ことを示すベンチマークは見つからなかった。結局、同じプロンプトで並べて比べるしかない。

## 比べ方

### 4 モデル × 6 題 × 2 スタイル × 3 シード

HiDream-O1 は diffusers に対応しておらず、専用リポジトリのスクリプトで動かす方式なので見送った<sup>5</sup>。Qwen-Image-2512 は重すぎる。残りの 4 つを比べた。

| key | モデル | ステップ | guidance |
|---|---|---|---|
| schnell | FLUX.1-schnell（int8 量子化、今の本番と同じ条件） | 4 | 0.0 |
| klein4b | FLUX.2 [klein] 4B | 4 | 1.0 |
| zimage_turbo | Z-Image-Turbo | 9 | 0.0 |
| zimage | Z-Image（base） | 30 | 4.0 |

設定は各モデルカードの推奨値に合わせた<sup>1</sup><sup>2</sup><sup>3</sup><sup>4</sup>。Z-Image（base）の推奨は 28〜50 ステップで、時間を節約するため 30 にした。

- **題材**: イルカのソナー 6 題（2 頭の通信、群れのネットワーク、司令塔、アイコンの運搬、探索、リレー）
- **シード**: 777 / 1 / 2 の 3 つ。構図がシードで変わるかを見る
- **環境**: Google Colab の L4（24GB）、diffusers 0.42.1。全モデルで model CPU offload を使い、1024×576 で生成した

### プロンプトの差を切り分ける

比べる前に、今のスタイル指定そのものが怪しいと気づいた。これまでは題材の後ろに、次の接尾辞を付けていた。

```text
soft pastel illustration, gentle lighting, warm colors, simple composition,
minimal background, cute and cozy atmosphere, high quality, detailed, artstation trending
```

題材側には `deep blue ocean, bioluminescent` と書いてある。`warm colors` と深海の青がぶつかっているうえ、`artstation trending` は Stable Diffusion 時代のおまじないである。

そこで、色域・コントラスト・質感を言葉で指定する接尾辞（以下 pastel）を作り、今の接尾辞（以下 soft）と両方で生成した。モデルを変えて良くなったのか、プロンプトを変えて良くなったのかを分けるためである。

```text
soft pastel color palette, light and airy, low contrast, gentle watercolor wash,
flat cute illustration, clean simple shapes, rounded soft edges
```

`white background` を入れる書き方もよく見るが、深海の題材と矛盾するので外した。schnell や Z-Image-Turbo は guidance 0 で動かすので、ネガティブプロンプトが使えない<sup>1</sup><sup>3</sup>。そのため「〜しない」ではなく「〜する」で書いた。

1 モデルあたり 36 枚、合計 144 枚。生成はすべて成功した。

## 結果

### 速度とメモリ

| モデル | 1 枚あたり（中央値） | ピーク VRAM |
|---|---|---|
| schnell（int8） | 24.8 秒 | 12.4GB |
| **klein 4B** | **16.1 秒** | **8.4GB** |
| Z-Image-Turbo | 24.0 秒 | 12.7GB |
| Z-Image（base） | 70.8 秒 | 13.0GB |

klein が一番速く、メモリも一番少ない。ステップ数は schnell と同じ 4 だが、schnell は int8 量子化と CPU offload の往復が重いぶん遅くなる。Z-Image（base）は 30 ステップなので約 3 倍かかり、36 枚で 40 分を超えた。

### アイコンを運ぶ絵（soft と pastel）

行がモデル、列がシードである。まず今の soft 接尾辞から。

![アイコンを運ぶイルカの比較（soft）。schnell は暗い青で足元に輪、klein はイルカを光る輪が囲み珊瑚が描かれる、Z-Image-Turbo は3シードとも同じ配置、Z-Image は光のループに沿ってアイコンが並ぶ](/blogimg/image-model/message_soft.webp)

schnell は 3 シードとも、足元に波紋が出る。ブログに載せた画像と同じ失敗が再現した。

次に pastel 接尾辞。

![アイコンを運ぶイルカの比較（pastel）。klein は水彩の淡い背景にパステルの珊瑚が入り一番ゆるふわ、schnell は深い青のまま](/blogimg/image-model/message_pastel.webp)

pastel にすると全モデルが明るくなった。ただし変わり方には差がある。

- **klein** は一番化けた。水彩の淡い背景にパステルの珊瑚が入り、狙っていたゆるふわに一番近い。soft のときはまだ暗めだったので、モデルとプロンプトの両方が効いている
- **schnell** は pastel にしても深い青のまま。色の指示があまり効かない
- **アイコン**は klein なら毎回出る。ただ、音波に乗って運ばれるというより、イルカの横に浮いている。運ばれている感じが一番出たのは Z-Image（base）で、光のループに沿ってアイコンが並んだ

### klein の弱点：シードで構図が変わらない

上の pastel の klein を横に見ると、3 シードとも「左右に 1 頭ずつ向かい合い、下に珊瑚」で、ほぼ同じ構図である。Z-Image-Turbo も同じ傾向だった。シードで構図が一番変わったのは Z-Image（base）である。

これはモデルカードの記述とも合う。Z-Image のカードは、Turbo を多様性 Low、base を多様性 High としている<sup>4</sup>。少ないステップで出すモデルは、構図が平均的なところに寄りやすいのかもしれない（klein のカードには多様性の記述がないので、ここは推測である）。schnell で感じていた「構図が毎回似る」は、klein に乗り換えても解決しない。

一方、輪の表現は klein が一番うまかった。リレーの題では、イルカからイルカへ光の輪が渡っていく絵になった。

![イルカのリレーの比較（pastel）。klein はイルカの間を光の輪が渡り、Z-Image-Turbo は点線の光でつながり、Z-Image は構図がシードごとに大きく変わる](/blogimg/image-model/relay_pastel.webp)

群れのネットワークの題では、Z-Image-Turbo の「円陣のイルカを光の線が結ぶ」構図がきれいだった。

![イルカの群れのネットワークの比較（pastel）。Z-Image-Turbo は円陣のイルカを光の線が星形に結ぶ](/blogimg/image-model/network_pastel.webp)

## 結論：klein ＋ pastel に乗り換え、Z-Image-Turbo と並べて選ぶ

パステル系のアイキャッチなら、FLUX.2 [klein] 4B に pastel 接尾辞を組み合わせるのが一番良かった。速くなるうえに、ゆるふわになる。ただし、良くなった分にはプロンプトの効果も大きい。schnell のままでも、色の指示が題材とぶつかっていないかは見直す価値がある。

運用は次のように変えた。

- **既定を klein ＋ pastel にした**。量子化も要らない
- **Z-Image-Turbo も同時にロードして、同じプロンプトで 2 枚並べて選ぶ**。題によっては Z-Image-Turbo の方が良かったためである。どちらも model CPU offload なので GPU には生成中のモデルしか載らず、L4 で問題なく回った
- **構図はプロンプトで指定する**。シードを回しても構図はほぼ変わらないので、`top-down view` や `wide panoramic view` のような視点・配置・頭数を書き分ける

比較で良かった 6 枚はアイキャッチ候補に加え、全二重音声 AI の記事のアイキャッチは klein 版に差し替えた。

![klein ＋ pastel で生成した2頭のイルカ。光る輪に囲まれ、文書やチャットのアイコンが浮かぶ](/blogimg/eyecatch/dolphin_sonar_exchange.webp)

構図の多様性が欲しい題では、Z-Image（base）が次点になる。ただし 1 枚 70 秒かかる。

## AI生成画像にラベルは要るのか

モデルを調べるついでに、「ローカルで生成した画像に AI 生成のラベルを付けるべきか」も調べた。

### 法的な義務はほぼない

| レイヤー | 義務 | 要点 |
|---|---|---|
| 日本の法律 | なし | AI 生成物の表示義務はない<sup>10</sup> |
| 景品表示法 | 条件付き | 表示しないこと自体は問題ない。ただし「手描き」「イラストレーター描き下ろし」などと書いて実際は AI だと、優良誤認のおそれがある<sup>11</sup> |
| EU AI 法 第 50 条 | ほぼ対象外 | 利用者側の開示義務はディープフェイク（実在の人物・物・場所・出来事に似ていて、本物と誤認されうるもの）が対象<sup>12</sup>。スタイライズドなイラストは一般に該当しないと解されている<sup>13</sup> |
| Google 検索 | 推奨 | 一般サイトには、コンテンツの作り方を読者に合う形で添えることを勧めている<sup>14</sup>。Merchant Center（EC）だけは IPTC メタデータが必須<sup>15</sup> |
| モデルライセンス | なし | Apache 2.0 に表示義務はない。Krea 2 は、法令やプラットフォームの規約が求める場合に開示が必須<sup>9</sup> |

パステル調のイルカの絵にラベルは要らない。ただ、次の 2 つはコストがほぼゼロなのでやることにした。

1. **画像に IPTC メタデータを埋め込む**（機械向け）。業界標準の付け方で、IPTC もサイト運営者にメタデータを消さないよう呼びかけている<sup>16</sup>
2. **サイトフッターに一行書く**（人間向け）。画像ごとにキャプションを付ける必要はないので、「アイキャッチ画像の多くは画像生成 AI で作成しています（画像にも AI 生成のメタデータを付与）」とした

ラベルを画像の近くに出すべきなのは、実在のものに見える写実的な画像や、商品の使用イメージを AI で作る場合である。このブログには当面ない。

### IPTC メタデータの中身

使うのは IPTC Photo Metadata の `Iptc4xmpExt` 名前空間である。AI 生成であることを示す `DigitalSourceType` は 2009 年からある。モデル名やプロンプトを書く `AISystemUsed` / `AIPromptInformation` などは、2025.1 版で追加された<sup>17</sup>。

```xml
<x:xmpmeta xmlns:x="adobe:ns:meta/">
 <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">
  <rdf:Description rdf:about=""
    xmlns:Iptc4xmpExt="http://iptc.org/std/Iptc4xmpExt/2008-02-29/">
   <Iptc4xmpExt:DigitalSourceType>http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia</Iptc4xmpExt:DigitalSourceType>
   <Iptc4xmpExt:AISystemUsed>FLUX.2 [klein] 4B</Iptc4xmpExt:AISystemUsed>
   <Iptc4xmpExt:AIPromptInformation>two dolphins exchanging glowing sound waves, ...</Iptc4xmpExt:AIPromptInformation>
  </rdf:Description>
 </rdf:RDF>
</x:xmpmeta>
```

`trainedAlgorithmicMedia` は「学習済みモデルが生成した画像」を表す。AI 生成の素材を含む合成画像なら `compositeWithTrainedAlgorithmicMedia` を使う。

### 新しく生成する画像：Pillow で保存時に書く

Colab の生成コードでは、Pillow で WebP を保存するときに `xmp=` を渡すだけで済む。

```python
img.save(out_path, format="WEBP", quality=85,
         xmp=build_xmp(model_id, prompt=prompt))  # build_xmp は上の XMP を組み立てる関数
```

Pillow のバージョンによっては黙って書かれない可能性も考え、保存後に読み戻して、XMP が無ければ警告を出すようにした。モデル名はロードしたパイプラインから、プロンプトは生成関数から自動で入るので、ノートブック側の操作は増えない。

### 既存の画像：webpmux で後付けする

すでにある WebP には、libwebp に付いてくる `webpmux` で XMP だけを差し込んだ。exiftool でも書けるが、手元には webpmux しかなかった。

```bash
webpmux -set xmp label.xmp in.webp -o out.webp   # 付ける
webpmux -get xmp out.webp -o -                    # 確認する
```

webpmux はチャンクを差し込むだけで、画像を再エンコードしない。付ける前と後の画像をデコードして比べ、画素が完全に一致することを確認した。

注意点が 2 つある。

- **`cwebp` で変換し直すとメタデータが消える**。`cwebp` の既定は `-metadata none` である<sup>18</sup>。変換し直したら付け直す
- **ビルドで消えないかを確かめる**。Astro は `public/` の画像をそのままコピーするので、`dist/` でも XMP が残っていた。画像最適化を通す構成なら、消えないか確認が要る

### 59 枚の棚卸し

既存のアイキャッチ 59 枚に付けるにあたって、1 枚ずつ出所を確かめた。

- **schnell 製（54 枚）**: 生成ログと照合して 47 枚。残り 7 枚は元ファイルが消えていたが、コミット履歴とプロンプト表から schnell と判断した
- **アプリ紹介カード（3 枚）**: AI を使っていないので付けない
- **出所が曖昧（2 枚）**: モグラの画像は ChatGPT Image 製だった。青い鳥の画像は昔すぎて分からなかったので、klein で作り直して差し替えた

### おまけ：埋め込んだモデル名を Gallery に出す

このブログには、アイキャッチを一覧できる [Gallery](/gallery/) ページがある。せっかくモデル名を埋め込んだので、ビルド時に各画像の XMP を読み、画像の下にモデル名を出すようにした。

```ts
function readAiModel(buf: Buffer): string | undefined {
	const xmp = buf.toString("utf8");
	const model = xmp.match(
		/<Iptc4xmpExt:AISystemUsed>([^<]+)<\/Iptc4xmpExt:AISystemUsed>/,
	)?.[1];
	if (model) return model;
	if (xmp.includes("digitalsourcetype/trainedAlgorithmicMedia")) return "AI生成";
	return undefined;
}
```

機械向けに埋めたメタデータが、そのまま人間向けの表示にも使える。画像の出所を管理する台帳を、画像ファイルそのものに持たせた形になった。

## まとめ

- FLUX.1-schnell でうまくいかなかった絵は、モデルだけでなく、プロンプトの色指定が題材とぶつかっていたのも原因だった
- Apache 2.0 の 4 モデルを比べ、FLUX.2 [klein] 4B ＋ pastel 接尾辞に乗り換えた。速く、軽く、ゆるふわになる。構図はシードでは変わらないので、プロンプトで指定する
- Z-Image-Turbo も並べて生成し、良い方を選ぶ
- AI 生成ラベルは義務ではないが、IPTC メタデータとフッターの一行で付けた。webpmux なら再エンコードなしで後付けでき、埋めたモデル名は表示にも使える
